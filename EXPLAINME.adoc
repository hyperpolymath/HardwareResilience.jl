== Claim 1: Guardian logic for long-running kernels with transparent fallbacks

[quote, README — Overview]
____
HardwareResilience.jl provides the "Guardian" logic for long-running kernels.
It detects hardware faults and handles transparent fallbacks.
____

*How it works:* `KernelGuardian` is a mutable struct (`src/HardwareResilience.jl`)
with fields `name::String`, `status::Symbol`, `max_retries::Int`,
`retry_delay_ms::Int`, and `failure_log::Vector{Tuple{DateTime,String}}`.

`monitor_kernel(guardian, op)` executes the zero-argument function `op()` inside a
retry loop. On exception it logs the error with `now()` timestamp and re-attempts
up to `max_retries` times. Delay between attempts uses exponential backoff:
`delay_ms = retry_delay_ms * 2^(attempt-1)`. If all retries are exhausted the
guardian transitions to `:degraded` status, emits a `@warn`, and returns `nothing`.
On any successful return the guardian self-heals back to `:active` if it was
previously `:degraded`.

*Honest caveat:* The retry loop is synchronous — it blocks the calling thread.
For genuinely parallel operations (CUDA kernels, multi-threaded Julia tasks) the
caller must wrap each task individually. There is no distributed-guardian
coordination mechanism.

== Claim 2: ECC memory, RAID, thermal zones, and watchdog detection

[quote, README — Features]
____
KernelGuardian: Monitor and track the status of critical kernels. Self-Healing:
Automated error handling and fallback logic.
____

*How it works (hardware detection side):* `detect_resilience()` calls five
detection functions and assembles a `ResilienceReport`:

- `check_ecc_memory()` reads `/sys/devices/system/edac/mc*/ce_count` and
  `ue_count` (Linux EDAC subsystem). Falls back to `dmidecode` if the EDAC
  sysfs path is absent.
- `check_raid_status()` reads `/proc/mdstat` for Linux software RAID. Parses
  the status line for `[UU]`/degraded indicators.
- `check_thermal_zones()` reads `/sys/class/thermal/thermal_zone*/temp` and
  trip points, constructing `ThermalZone` structs. Marks zones as critical if
  current temperature exceeds the critical trip point.
- `check_watchdog_timers()` lists devices under `/sys/class/watchdog/`.
- `check_redundant_power()` scans `/sys/class/power_supply/` for multiple AC
  adapters as a proxy for redundant PSU presence.

`overall_resilience` in the report is computed as `:high` (ECC + RAID + OK thermal),
`:medium` (some protections), or `:low` (no protections).

*Honest caveat:* All detection is Linux-only. Non-Linux platforms receive stub
results with `present=false`. Hardware RAID controllers (LSI, Adaptec) are not
probed — only Linux software RAID via `/proc/mdstat`. The PSU detection is a
heuristic — it counts power supply entries, not actual hardware redundancy.

== How It Is Checked

Tests live in `test/runtests.jl`. Coverage includes:

- `KernelGuardian` construction with various `status` values
  (`:Healthy`, `:Degraded`, `:Failed`, `:Recovering`, `:Unknown`)
- Mutability: `status` and `name` fields can be updated
- `monitor_kernel` returns op result on success (integer, string)
- `monitor_kernel` returns `nothing` on `error()`, `DomainError`, `BoundsError`
- Retry count exhaustion transitions guardian to `:degraded`
- Exponential backoff timing is within acceptable range
